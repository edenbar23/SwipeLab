# Testing Setup and Guidelines

This document outlines the testing strategies, profiles, and common pitfalls encountered in the SwipeLab backend testing environment.

## Test Profiles

We utilize distinct Spring profiles for different testing contexts to manage how the database schema and application context are initialized.

### 1. `test` Profile
- **Usage**: Standard unit tests or slice tests that require minimal context.
- **Database**: H2 In-Memory Database.
- **Schema Management**: Flyway is **enabled**. Hibernate `ddl-auto` is typically set to `validate` or `update`.
- **Note**: If your test involves entities that are auto-generated by Hibernate *and* Flyway attempts to run migrations, you might encounter `Table already exists` errors.

### 2. `integration` Profile
- **Usage**: Full end-to-end integration tests within the Spring context (e.g., testing asynchronous event listeners, complex transactions).
- **Database**: H2 In-Memory Database (`MODE=PostgreSQL`).
- **Schema Management**: Flyway is **disabled**. Hibernate `ddl-auto` is set to `create-drop`.
- **Why?**: Some of our Flyway migrations contain PostgreSQL-specific SQL syntax (like `ON CONFLICT DO NOTHING`) that the H2 database parser cannot handle. By disabling Flyway in `integration` mode, we allow Hibernate to purely construct the schema based on JPA entity annotations, bypassing Postgres-specific quirks.

## Common Testing Pitfalls

### Testing `AFTER_COMMIT` Event Listeners
When testing asynchronous components triggered by `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`, standard `@Transactional` test methods **will fail** to trigger the event. 
- **Reason**: Spring's `@Transactional` on a test method automatically rolls back the transaction at the end of the test to keep the database clean. Since the transaction is never committed, `AFTER_COMMIT` is never reached.
- **Solution**: Remove the `@Transactional` annotation from your test class/method. Manually clean up the database in an `@AfterEach` teardown block using repository `deleteAll()` methods. Use `Thread.sleep` or `Awaitility` to wait for the async thread to finish before asserting.

### DataIntegrityViolation Exceptions on Mock Data
When building mock entities (e.g., `Task`, `User`) in `@BeforeEach` setup methods, ensure you populate all fields that correspond to `NOT NULL` database constraints.
- **Example**: Our `Task` entity utilizes auditing fields. If you construct a `Task` without explicitly setting `.createdBy("admin")` or a required `status`, the repository save operation will throw a `DataIntegrityViolation` exception. Always mirror the required constraints defined in the Flyway migrations when constructing test mock data.
